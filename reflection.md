# Reflection

For Problem 5 we built a small interactive page that covers two of the topics from this sprint, timing side channels and algorithmic complexity. We picked these two because we had already spent Problems 2 through 4 actually finding and exploiting these exact kinds of bugs in real code, so we figured a visual version of what we had just done by hand would help other students (and honestly ourselves) see the idea more clearly than just reading about it.

The first tab recreates the password checker from Problem 2. You can type a guess and see how many characters are wrong, or hit a button that runs the same character by character attack we wrote earlier, locking in one correct letter at a time instead of guessing the whole password at once. Watching it actually crack "password123" live, character by character, made the idea click in a way that just reading the explanation did not. It is one thing to say a program leaks information through a side channel, it is another to watch a page figure out a password in a few seconds because of that leak.

The second tab is a chart you can control with a slider that compares a normal loop, a nested loop, and an exponential blowup as the input size grows. We used a log scale on purpose, because on a normal scale the exponential line just disappears off the top of the chart almost immediately, which actually hides how dramatic the difference is. Seeing all three lines on the same chart, with the same tiny change in input size producing a barely noticeable change for one line and a massive change for another, is basically the point of Problem 3. We were careful not to lump Problem 4 into that same exponential framing though, since the Rectangle bug is really a different kind of failure, a shared static pointer that creates a cycle, not a per step cost that explodes, so we call that out separately in the app instead of overstating the similarity.

For our workflow, we used AI assistance to help build the page itself, mainly for writing the JavaScript logic and the chart drawing code, since neither of those were things we wanted to spend the limited time on this sprint hand coding from scratch. We gave direction on what we wanted each tab to teach and how we wanted it to feel, and went back and forth testing it in the browser until the interactions actually matched what we were trying to show, including catching a bug where the complexity chart was not rendering at all because the canvas was sized to zero while its tab was hidden on page load.

Building this helped us connect the dots between the four problems in this sprint. Problem 2 showed us a timing leak in isolation, Problem 3 and 4 showed us algorithmic complexity blowups in isolation, but putting both into one small app made it clearer that these are really the same underlying lesson, a program that reveals more than it should, whether that is through time, through a count, or through how much work it ends up doing, can be turned against it.
